## Notes per finding

**1 and 2. /community.** Four late states, four fixes, one principle: every list is drawn at its loaded geometry and nothing late sits above something already on screen.

- (a) The online pill. Its text now sits in one grid cell with an invisible "888 players online" sizer, so the pill keeps its width when the count replaces the loading line (now "Counting players…"). It used to shrink from "Connecting to the lobby…", which let it rejoin the h1's row on a phone and lift the grid 37px. After: the pill appears in no after finding.
- (b) Rail skeletons. `RailSkeleton` (32px rows on an 8px gap, 3/4/5 rows regardless of the list) is replaced by `ListSkeleton`, which draws each list's own margin, row height, gap and count: 5 rows of 40px for Top players and Active this week, 5 of 44px for Clubs, 4 of 44px for Tournaments. `ListReserve` keeps that height as the list body's floor, so a shorter list, the empty sentence or the error line leaves the panel the same height instead of pulling every panel below it up. Empty and error lines are centred in the reserve so an empty rail reads as an empty panel. Trade-off, stated plainly: with little data (the dev database has no rated games, one club and one event) the rail panels show blank space under the one line. In production Top players and Active this week fill all five rows. A server-rendered first page of rail data would remove the need for the floor; that is a proposal, not built (below).
- (c) Friends card. Its skeleton is now 3 rows of 44px on 1px dividers with the same floor, so an empty roster no longer collapses under Recent games. The card still enters late when the session has no `nc_who` display cookie. That happens once per browser (the first `/api/auth/me` sets the cookie), but the harness's seeded `user` session never has it, which is why the round 1 harness `user` cells showed the Friends card entering (1280 user 0.059, 360 user 0.30-0.37). Round 2 (f) holds its place, and both `user` cells are now under 0.01 without the cookie.
- (d) Recent opponents moved below Recent games, last in the main column. It needs the full user and then a games fetch, so it always lands seconds after everything else; above Recent games its arrival pushed that card down. At the end of the column it pushes nothing on desktop.
- (e) Recent games, round 1 (a regression): a 12-row skeleton with no floor. Any feed shorter than 12 (the empty dev database, a fresh deploy, a quiet period) collapsed the card and pulled the rail up into view on a phone: 360 signed-out 0.212 and 360 user 0.369, both worse than before. Round 1 of this doc called that a dev-only quirk; it was not, since nothing guarantees a full feed.
- (e) Recent games, round 2 (the cause): the first page of the feed is read on the server. `page.tsx` is now a server shell that calls `readRecentGames()` (`src/app/community/recentGames.ts`, the same query and shape as `/api/community/recent`) and passes the rows to the client page (`CommunityClient.tsx`, the old page body), so the list is in the HTML at its real length, whether that is 0, 5 or 12 rows. The read has a 1.2s budget; past it, or on an error, the page renders without it and the client loads the list behind the 12-row skeleton as before, and Retry still uses the API. The row's "N ago" label carries `suppressHydrationWarning`, since the age can tick over between the server render and hydration. The rename moved the file's entries in the `check-buttons.ts` and `check-reduced-motion.cjs` baselines (a move, not new debt).
- (f) Unknown session, round 2: with a session cookie but no `nc_who` hint (the harness `user` state, or a session from before the hint existed), `display` is undefined at first paint and the Friends card used to enter once `/me` answered, pushing Recent games and the rail down 209px on a phone. The page now draws an unlabelled Friends-shaped skeleton (same plate, header row and list floor) while `display` is undefined. If that visitor turns out to be a guest the skeleton gives way to the sign-in nudge; that case needs a legacy guest session with no hint and was not measured.

**3. /friend and /lobby pill.** `/friend` is a server redirect to `/lobby?tab=friends` (F037), so both cells measure the lobby's `StatusPill` in `src/app/lobby/page.tsx` (slice B, core). Same class as 1(a): "Connecting…" and "Live · N players" differ in width, and the row it sits in reflows. Suggested fix for core: the same stacked sizer used on /community (one grid cell holding the live label and an invisible "Live · 888 players"). Not edited here.

**4. Console 401s.** `/friend` signed-out: `FriendsPanel` fetched `/api/friends` on mount, before the header had minted the guest, got 401, and then kept the signed-out view for a guest who can in fact add friends. It now reads `useSession({ ensure: true })`, loads once per account when the session is known, and a failed mint (null) is the signed-out view with no request. `/mod/house` personas 401/403 is in `src/app/mod/*` (slice G); the same pattern (read the session, skip the call unless `role` is mod or admin) applies there.

**5. Guest mint.** Root cause in the finding is right: pages called `useSession()` without `ensure`, which returns `display: null` while the header's guest mint runs. The server accepts guests for every action these pages offer (club membership, tournament entry, DMs, creating a club or an event: each route only checks for a session). Fix in the pages, not in `SessionProvider` (slice A): the inbox list, the thread, the club page, the club directory, the tournament directory and the tournament page now pass `ensure: true` (the mint is shared, `ensureAccount` dedupes it). While the answer is unknown they draw the guest's eventual frame: the inbox draws the search box and list skeleton, the thread draws its loading bubbles with Send disabled, the club and tournament pages draw a disabled Join button so the slot does not fill in late. Only a failed mint (null) shows a sign-in prompt, so "Sign in to join" (F036) remains for that case. The thread's send got a ref guard on the way (two Enter presses in one task posted twice), and so did club join/leave and tournament join/withdraw (F179 class; the server calls are idempotent, but the second POST is wasted).

**6. TV.** `role="status"` on the loading list with an sr-only "Loading live games"; the three skeleton bars are `aria-hidden`. Sibling grep: the only other `aria-label="Loading…"` in D files is on the thread's skeleton `<ul>`, where the label is allowed (list role) and the pane already carries `aria-busy`.

**8. Error lines.** Grep of D files for `text-oxblood-glow` lines without a role found the listed seven plus the FriendsPanel add note; all eight are covered.

**9. Listbox.** The Recent dropdown is one grid with two columns. The listbox (options only) and the Remove column are both `grid-rows-subgrid` children spanning the same rows, so each option and its Remove button share a row height whatever the content (two-line rows included). Keyboard behaviour is unchanged (`aria-activedescendant` on the input, arrows move through options); the Remove buttons stay in the tab order after the options, and hovering one highlights its row.

Calling `/api/auth/me` once before saving the state would make the `user` cells measure the usual returning visit (this is how `cls-community-returning-after.json` was taken).

## Proposal (not built)

P-community-ssr: Recent games is server-rendered as of round 2. The rest of the public data (top players, clubs, events, active this week) could be rendered on the server the same way and pass it in as the first state, as `/tv` already does for its shell.
