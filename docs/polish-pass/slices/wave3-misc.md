## Notes

**1. /mod/house.** 771be5a (wave 2 mod) had already gated the roster fetch on `isMod`, so the 401/403 console errors from the wave 2 social finding no longer happen. I measured this again for this pass (console guard over signed-out, guest, user, mod and admin, plus the probe's per-response check) and it holds. What was still wrong is what the page shows when the roster request does fail. A transport or 5xx failure printed "Try again in a minute." with nothing to press. It now uses the shared `LoadFailed` (message plus Retry, `role="alert"`) that the other mod sections use. A 401 or 403 means the server no longer accepts this session as staff: it was signed out elsewhere, or its role was removed after the page loaded. Retry cannot fix that, so the page says so and links to sign in again. The effect also got a cancel flag, so a late answer after unmount is dropped. In dev, React strict mode can fire the roster request twice on mount. Production does not, and the probe accepts one or more requests as long as each returns 200.

**2. Recent games.** This is a move, not a rewrite. The SQL, the `LIMIT 12`, the category fallback and the output shape are exactly what both copies had. `RecentGameRow` in the lib matches `RecentGame` in `CommunityClient.tsx` structurally, and tsc checks the assignment in `recentGames.ts`. The dev database has no finished games, so the byte-for-byte comparison was on an empty list (`{"games":[]}` before and after). The code path is the same function either way.

**3. Skeleton hold.** The show-delay was already CSS: 757e679 in wave 2 added `--skeleton-delay: 150ms`, opacity only, with the box kept. What was missing was the minimum duration, which needs to know when the data arrived. `useSkeletonHold(loading)` in `src/components/ui/useSkeletonHold.ts` records when the skeleton was committed. When loading ends it works out whether the skeleton ever became visible (commit plus 150ms). If it did not, the content goes in at once. If it did, the content waits until the skeleton has been visible for 400ms. The swap runs in a layout effect, so a fast load never paints an extra frame of the invisible skeleton. The hold never holds an error: callers check their error first. It changes when the content replaces the skeleton, not the geometry of either, so it cannot add CLS. That was measured on /community, /leaderboard, /clubs, /tournaments and /inbox, all under 0.01 (`wave3-misc-cls-after.json`). Where it is applied: the six /community lists (friends, recent, top, clubs, active, the tournament rail), the /leaderboard table (every tab switch clears and reloads it), the /clubs and /tournaments directories, the /inbox conversation list, and the friends panel on the lobby's friends tab. The jump-to-me scroll on /leaderboard now also re-runs when the hold ends, so a jump never looks for a row that is still behind the skeleton.

How it was measured: the probe loads /leaderboard, caches each ladder's answer, then switches tabs with the answer held for 0, 60, 260, 600 and 1200ms. It times from the click to the skeleton entering, becoming visible (opacity above 0.05) and leaving. It does this twice.

**Review fix, hard loads.** Review found that the hook started its clock in its layout effect, which on a hard load runs at hydration. On /leaderboard, /clubs, /tournaments, /inbox and the /community lists the skeleton is in the server HTML, so its CSS show-delay ran from first paint, often a second or more before hydration, and the hook then held content up to about 400ms more after the data arrived. The hook now detects that it is hydrating (`useSyncExternalStore` returns its server snapshot only in the hydrating render). For the loading spell that is already on at hydration, it starts the clock at the first-contentful-paint entry (else first-paint, else the time origin). Client-rendered skeletons (tab switches, client navigation, any later loading spell) still start at commit. `scripts/polish/misc-w3-hardload.mjs` (the reviewer's probe, with two rounds and a 600ms delay added) does a hard load of /leaderboard with the /api/leaderboard answer held for 0, 100, 200, 300 and 600ms. In every run the skeleton had been visible for 0.9 to 2.2s before the answer.
