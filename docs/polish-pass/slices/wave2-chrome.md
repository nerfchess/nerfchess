## Notes per finding

**1. Account menu.** The finding asked to put `aria-haspopup="menu"` back. The panel is not an ARIA menu: its items are plain buttons in the tab order, with no `role="menu"`/`menuitem` and no arrow-key roving. `aria-haspopup="menu"` tells a screen reader user it is a menu button, and they then press arrow keys that do nothing. The honest pattern for this panel is a disclosure: `aria-expanded` plus `aria-controls` naming the panel (`id="site-account-menu"`). The spec comment already called the items "menu buttons", so it now finds the trigger by its accessible name and asserts `aria-expanded="true"`. If the owner wants a real menu button, that means adding `role="menu"`, `menuitem` roles and arrow-key roving. Commit 31f93d5 also carries the SiteHeader half of row 8 (popover exits and the hover dropdown), because the file was staged whole.

**2. Primary button.** It is one token pair, so the fix is in one place. The fill moves to the accent's existing dim rung, `--accent-dim-rgb`, which applyUiPrefs and the pre-paint script already stamp per theme. Before this nothing read it. No new colour. Contrast with the white label: dark 5.25, midnight 4.73, light 6.84 (was 3.27, 2.79, 4.52). The hover lift drops from brightness(1.15) to (1.08), so hover stays at 4.62 on dark (1.15 would give 4.15). Midnight hover is 4.17; that is the one transient state under 4.5. Links, focus rings and `--accent` fills elsewhere are unchanged. The primary button is now visibly a deeper blue than the link colour. This is reversible in one line if the owner prefers the brighter fill with a larger label. /friend's 4 contrast nodes (`bg-[color:var(--accent)]` and others) are not `.btn-leaf`: handed to social.

**3. Arena host.** next.config.mjs (slice L) bakes the production arena in as the `NEXT_PUBLIC_ARENA_URL` default. Editing it would restart the shared dev server, so the gate went into the client instead: under `NODE_ENV=development` the production host counts as unset. An explicit non-production URL, such as a local arena, still works. Production builds are unchanged.

**7. framer gate.** Once imported, `installFramerGate` sets `MotionGlobalConfig.skipAnimations` from `html[data-anim]` and follows it with a MutationObserver. That covers all 21 framer call sites in GameOver, OnlineMatch, OpponentDraftViewer, DraftOverlay, Board, Pocket and WaitingCornerNotice without touching them. The /dev/motion harness gains a `framer-probe` fade as a stable target for the check, since the bot game's framer entrances play before any probe can sample them.

**8. Nav hover dropdown.** The wave 1 comment said "no opacity fade" so the labels never read as half-transparent. The dropdown now switches `display` instead of `visibility`, so the shared `.m-pop` enter (200ms, the same as every other popover) replays on each open. It has no exit on purpose: sweeping the pointer along the bar would otherwise leave a fading menu under the next one.

**10. Scrim alpha.** The chrome sites keep their alphas (MobileNavMenu /40, SettingsPanel /70, targeting /80). Picking one alpha across all 15 sites changes other areas' files and how heavy each overlay looks, so it is a proposal: add `background: rgb(0 0 0 / 0.6)` (or a `--scrim` token) to `.m-scrim` and drop the per-site `bg-black/NN`.

**12. Skeleton.** The delay is 150ms (`--skeleton-delay`), with an opacity-only fade on --dur-1. The block keeps its box, so there is no CLS. It also holds with Animations off, because it is not motion (the backstop clamps durations, not delays). A minimum on-screen duration needs JS state per skeleton and was not done; with a 150ms show-delay the worst case is a skeleton visible for a few frames, which reads as a fade rather than a flash.
